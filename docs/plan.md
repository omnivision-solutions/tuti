## How we work from Phase 4 on

Every change is a small PR (one topic, squash-merged) that CI proves before it lands:
lint, typecheck, unit, database and browser tests, production build. An agent opens
the PR, stays with it until checks and review bots finish, answers every finding
(fix it or rebut it with evidence), then merges. Each phase below lists the tests it
adds; a feature isn't done until its tests are in the PR.

Test layers (set up in Phase 4):

| Command | Real | Faked | Runs |
|---|---|---|---|
| `pnpm test` | product logic | everything external; no database, no keys | every PR |
| `pnpm test:db` | Postgres (pgvector, pg_trgm), Prisma, Better Auth, server actions, worker tasks | OpenAI, Hatchet (jobs run inline), email, GitHub | every PR |
| `pnpm test:e2e` | production build of web + inline jobs in a browser, portal subdomains on `*.localhost` | same as above | every PR |
| `pnpm test:live` | real OpenAI / Claude / GitHub / email | — | by hand; a missing key means "not run", never "passed" |

## Licences: hiding "Powered by tuti" (asked 2026-10-21)

The badge is Tuti's attribution on every portal, so hiding it is paid: a flat monthly fee per project of an installation, on tuti.so and self-hosted alike. The fee is $49 a month per project, on tuti.so and self-hosted alike (decided 2026-10-25). Who can buy it: projects on a paid plan on tuti.so, and self-hosted projects; a project on tuti.so's free plan can't (see Plans). Tuti signs each licence key with its private key; installations trust only the public keys in the code (no setting, env var or database edit replaces them), so getting around it means forking, which the licence terms cover. Keys come from tuti.so only: bought on tuti.so, then fetched and renewed by the installation (no pasted keys for now).

- [x] "Powered by tuti" links to tuti.so on every installation (it linked to the installation's own `APP_URL`)
- [x] Enforcement: an installation id (random, made by the migration); a licence key is `{ installation, project, exp }` signed with Tuti's Ed25519 key, checked offline against the public keys in the code. The portal shows the badge unless the project has a valid key (so turning `poweredBy` off in the database isn't enough), and `branding.update` refuses to hide it without one
- [x] Licence server on tuti.so (only where `LICENSE_PRIVATE_KEY` is set): licences per installation + project, and `POST /api/license/refresh`, which returns a key for about 35 days and a new one-time refresh token. A reused token means the installation was cloned: refused and logged. Except a lost response: each attempt carries a random request id the installation saves before sending, and until the new token has been used once, a retry with the previous token *and the same request id* gets the same answer again. The previous token with any other request id (a clone) is reuse. `tuti.so/license?installation=…&project=…` shows both ids (read-only) and how to buy (an email to hello@tuti.so at first; Stripe Checkout since 2026-10-26, below); a maintainer script (`scripts/license.mjs`) activates, cancels, or resets a licence's token chain (support's answer when a clone won the race). Tokens are derived from the private key, the licence and a generation, so none is stored
- [x] Installations renew their keys (`server/license-renewal.ts`): after a portal page (in `after()`, once the page is sent, never awaited by it), at most daily, on every installation whether jobs run on Hatchet or inline, so there's no separate daily job; a quiet portal renews on its next visit, which shows the badge only if the key expired meanwhile. One check per project at a time (a 30-second lease on `licenseCheckedAt`), so two can't spend the same token; the request id is saved before sending. Every call to tuti.so has a 10-second timeout: tuti.so down or answering badly keeps the current key until it expires; a refusal (cancelled, or in use on another copy) removes the key and token, so the next check is a new claim (which works after support resets the licence). Keys that don't verify aren't kept. Keys expire by the latest time tuti.so reported (setting the clock back doesn't help). "Check now" as `license.check`, which also starts the checks: an installation only contacts tuti.so for a project once an admin asked for its licence, or while it has one. The README says what it sends (installation id, project id, refresh token once it has one, request id, app version). `LICENSE_SERVER_URL` points tests at a local server (keys from any other server don't verify)

## The "shipped loop" (Phases 7–11)

Code is the source of truth. One GitHub connection feeds everything after it: each
merged PR is analysed into proposed actions (the feedback it resolves, the docs it
changes, its changelog line) that the team applies, and the AI answers from those docs. Questions the AI can't answer
become doc drafts or feedback posts. (Inspired by Ferndesk's self-updating docs and
opendesk's help center + AI; neither closes feedback from releases.)

Rules for every AI feature: optional (off without an API key, like embeddings),
nothing customer-facing publishes without a team member's approval, every answer
or proposal shows its sources.

## Code changes: a review for every merged pull request (asked 2026-10-23)

Renamed **Autopilot** on 2026-10-30, and its updates may now go out by themselves after a hold: see Autopilot below.

Nobody links pull requests to posts, and there's nothing to set up beyond the repositories. Every pull request merged on a project's repositories is analysed once: which open posts it resolves or moves forward, which articles it makes wrong or incomplete (or which new one it needs), and what the changelog should say. The result is one **code change** in the team app, linked to the pull request, with a list of proposed actions the team applies, edits or dismisses (like Ferndesk's "Code change" threads, which do this for docs only; Tuti has the feedback too). Nothing customer-facing changes until someone applies it (the shipped loop's rule), so a post is completed, and its voters emailed, when the team applies "resolves", not when GitHub merges or releases.

Deciding and writing are separate steps (see Deciding vs. writing): a decision model answers bounded questions with a probability (does this change anything users see? does it resolve this post? does it make this article wrong?), and the LLM only writes for the pairs that pass (the summary, why, the article edits, the changelog line). That keeps cost per merge low, makes the thresholds measurable, and lets each project's applied and dismissed actions calibrate them.

- [x] Cleanup first (no customers yet, nothing to migrate; done 2026-10-23): drop the Shipping setting (`closeOn`; completing posts on merge or on a release), In progress on open, the pull request comment (`commentOnPullRequests`, `github_pr_comment`), reference linking (`tuti#12`, post URLs), embedding link suggestions (`link_suggestion`, `linkSuggestions.*`) and "Link PR" on the post view (`links.add`). Kept: repositories per project, the changelog's running draft (merged pull requests, closed by a release), post links (written by applied actions; `links.remove` for a wrong one), the shipped emails (sent when a post becomes Completed, however it does)
- [x] Ingest on merge (a `code-change` job, one at a time per pull request, retried, idempotent): title, description, labels, commits, author, changed files and the diff, read with the installation token, without lockfiles, generated or binary files, capped per pull request (a bigger one is read file by file). Stored as `code_change`: project, repo, number, URL, title, author, merged at, state (analysing, ready, nothing to do, failed), summary, why, and the writing and decision models' versions. The App needs Contents: read (to read files around the diff) Done: the `github-pull-request` job makes the code change (one per pull request: a redelivery finds it) and queues `code-change` (one run at a time per code change, retried with backoff; one already analysed isn't read again unless asked). It reads the pull request, its commits (the first lines of the last 50) and its changed files with the installation token: each file's diff is GitHub's patch for it, capped (6,000 characters a file, 20,000 in all, so the decision model stays out of its slower long-context mode; files past it are listed, not read); a file GitHub sends no patch for (too big) is read from its start at the merge commit (Contents). If GitHub won't give it, the code change is `failed` ("GitHub didn't let Tuti read the pull request.") until a retry or a redelivery reads it
- [x] Gate: "does this change anything users see?" (labels, paths, title, the diff). If not, the code change says "Nothing to do" with the reason, collapsed in the list, with "Analyse anyway". The same decision replaces the running draft's fixed skip labels (`chore`, `internal`, `deps`). Done: a choice for the decision model (users notice it; only the team: refactoring, tests, CI, tooling; dependency updates; the repository's own docs), below 0.5 for users it's `nothing to do`, its reason the likeliest other answer ("Only the team sees this: refactoring, tests, CI or tooling.", "Dependency updates, with nothing users would notice.", "Only the repository's own docs changed."); analysed again on request (`force`), and "Analyse anyway" (`pastGate`, kept by a retry) skips the gate; folded away at the end of the list, with "Analyse anyway". With code changes on, a merged pull request goes into the running draft whatever its labels, and the gate's nothing to do takes its bullet out again while the draft collects (a failed analysis leaves it in); without them, the labels still decide
- [x] Candidates: the open posts (`post_embedding`) and article sections (`article_chunk`) nearest the change's summary, plus posts the pull request names (`tuti#12`, a post's URL): a strong signal for the decision, not a command. A few per kind, so the decisions stay cheap. Done: the summary for users is written first and embedded; the 5 open posts nearest it (not completed, closed or merged into another) and the 3 published articles with the nearest section, plus open posts it names (`tuti#12`, or a post's URL at one of the portal's addresses), marked as named in what the decision model sees
- [x] Decide per candidate, with a probability: a post is resolved, moved forward or unrelated; an article is now wrong, missing something or unaffected; and, once per code change, whether it needs a new article (what users can now do that no candidate article covers). By a decision model through OpenRouter, like the rest of the AI (`OPENROUTER_API_KEY`), such as TypeSafe's Jev (bounded answers with calibrated probabilities, much cheaper and faster than a chat model), set apart from the writing model: `DECISION_MODEL`, never `AI_MODEL`, defaulting (like `AI_MODEL` does) to the one the evaluation set picks among OpenRouter's, so it needs no setting. If OpenRouter can't serve the decision model, the analysis fails like any other error (the code change shows Failed, with Analyse again); merged pull requests still reach the running draft. No chat-model fallback (decided 2026-10-23: decision models are well tested, and a second path is more to build and test); later a per-project model learnt from applied and dismissed actions. Per action kind, below a threshold it's dropped, in between it's proposed as "maybe", above it as likely. Done: one request per candidate (the pull request, the summary and the post or article), with OpenRouter's Decisions API (`decide` in `@tuti/shared`); a post's choice is resolves, moves forward, related or unrelated (resolves or moves forward when either passes, the likelier; else links when the three together pass), an article's is wrong, missing something or unaffected (an edit when the first two together pass, saying which), and a new article is yes or no, asked once with the candidate articles' titles. Thresholds (`THRESHOLDS`, maybe / likely): resolves and moves forward 0.4 / 0.75, links 0.65 / 0.85, an article edit 0.4 / 0.75, a new article 0.5 / 0.8, from the evaluation set (links was 0.5: two false links at 0.58 and 0.61). On 2026-10-23 the evaluation set (63 decisions) ran three times against each decision model OpenRouter has: `nace-ai/drex-max` got every one right each time, `liquid/d1-ultra` all but one post, TypeSafe's `jev-1.14` 93–100% (it varied from run to run), and `openai/gpt-6-luna-decisions` the fewest (70% of posts), so `DECISION_MODEL` defaults to `nace-ai/drex-max`. A decision model OpenRouter can't serve fails the analysis (Failed, with Analyse again). ## Deciding vs. writing: small models for decisions (cross-cutting, asked 2026-10-20)

Generative models write; where the output is a decision (yes/no, a score, a ranking), a small model decides instead: cheaper, faster, calibrated, deterministic in tests, and it can learn from what teams already do in Tuti (merges and "not a duplicate", 👍/👎 on answers, "I don't know", dismissed gaps, edits to AI drafts). Small enough for self-hosters: a CPU reranker (ONNX, e.g. bge-reranker-base via onnxruntime-node) or logistic regression in TypeScript/SQL; no GPU, no extra service. Each starts from today's fixed thresholds and calibrates per project as labels accumulate.

Labels must mean one thing: an "I don't know" today can be no section close enough, no valid citation, or an article unpublished while the model wrote, so the question log records the cause before it trains anything (done: `docs_question.cause` is `no_relevant_section`, `no_valid_citation` (the model gave no answer or cited none of its sections; the two aren't told apart yet), `source_unpublished` or `off_limits`; questions from before it are `unknown`; the Gaps list shows it as a label). Learned artifacts (examples, models, thresholds, caches) are per project: one project's model or cache never answers for another or reveals its labels or content, they're deleted with the project, and a project can opt out of learning from its data.

- [ ] Reranker + calibrated per-project thresholds instead of the fixed ones: duplicate suggestions (similarity cut-off), AI answers' "can we answer this?" (`ANSWER_MIN_SIMILARITY` 0.4; the question is embedded first, and the gate decides whether the answer-writing model is called), help search (`SEARCH_MIN_SIMILARITY` 0.3); judged on a fixed evaluation set so the change is measurably better, not just different. Each decision gets its own contract, since today's numbers are cosine cut-offs for `text-embedding-3-small` and mean nothing for a reranker or classifier score: the score and its calibration, what it's evaluated on, the labels needed before a project's own model replaces the default, the fallback until then (a cold start or too few or one-sided labels), model versions, and rolling back when a new one does worse

## Support inbox (asked 2026-10-26)

A project's users can reach its team in one place: they write in the widget (or ask for a person after an AI answer) or email the team's support address, and every message lands in one inbox in the app. The team sees who's writing (the user's properties, groups, posts and other conversations), answers, assigns and closes. A reply reaches the user in the widget while they're there, and by email when they aren't; their email reply continues the same conversation. A user can have any number of conversations. Replaces "Support inbox, or hand-off to Intercom / Zendesk / Help Scout first" (Later) and the "live chat" left over from escalation (Phase 11).

Reviewed first: OpenDesk (useopendesk/opendesk, 2026-10-26; Apache-2.0, so its code may be borrowed into AGPL-3.0 with its notice kept, though its server is Go and Elixir, so we take designs, not code). Taken from it: one private address per project that the team forwards its support address to; receiving as a signed POST of the raw message, so any mail server or service can deliver it; the raw message stored first and read by a job, with a status and a reason for every one; the order replies are matched to conversations in; loop and auto-reply rules; how long the user has been waiting instead of read state per teammate; emailing a chat reply only when the user hasn't seen it after a minute; presence from the widget's last request rather than sockets. Done differently: replies are sent over SMTP (no Gmail or Microsoft APIs; SES's API only adds teams' domains); live updates are Server-Sent Events from the app itself, without OpenDesk's NATS and Phoenix gateway; users are identified by the SSO token Tuti already has, not a second HMAC; far less to start with (no SLAs, snoozing, saved replies, side conversations, voice or apps).

Decided (proposed 2026-10-26, confirmed by the user 2026-10-27):
- **Words.** "Inbox" in the sidebar; a "conversation" with "messages"; the team "replies". Never "tickets" or "contacts" (design.md's copy rules): the people writing are the project's users.
- **Data.** Three tables, each with `projectId`:
  - `conversation`: a number per project (`#12`), a subject, its status, its assignee (a team member or nobody), where it began (widget, email, an AI answer, the API), the user (`userId` when Tuti knows the person: an SSO user or a portal account; else just the email, lowercase, with whether it's verified, and a signed-out visitor's token, hashed), the email reply token, `spam`, `lastMessageAt`, and `waitingSince` (the user's oldest message the team hasn't answered).
  - `conversation_message`: the author (the user, a team member, the AI, Tuti), the channel (widget, email, API), plain-text body (links kept; email turns HTML into text without the quoted reply, and keeps the original), whether it's an internal note, the email headers (`Message-ID`, `In-Reply-To`, `References`; unique per project only for the `Message-ID`s Tuti sends, since received mail is deduplicated by `inbound_email` and two senders may reuse one), the SES message id of a sent one, when the user saw it, and how it was emailed (pending, sent, failed, delivered, bounced, complained; it only moves forward, see Sending).
  - `inbound_email`: the raw message (up to 25 MB, attachments included; deleted once it's read into a message or ignored, and a failed one after 30 days, so raw bodies don't pile up), its `Message-ID` (used for threading; a redelivery is a no-op because the `Message-ID` and the sender together are unique per project, so another sender reusing a `Message-ID` is still kept, and a message without one is keyed by a SHA-256 of its raw bytes instead), status (received, added, ignored, failed) and why.
  - Attachments are `conversation_attachment` rows linked to a message (the file kept whole in the media storage), signed like today's private media (see the attachments item).
- **Statuses.** Open (the team owes a reply), Waiting (the team replied last; set by replying, or by hand while the team's reply is the latest: a reply kept open by a follow-up it answered too) and Closed (by hand). A message from the user opens a waiting or closed conversation again. No per-teammate unread state: Open plus `waitingSince` says what needs an answer.
- **Who's writing.** In the widget, signed-in users (the page's `identify`, or the portal's sign-in) and signed-out visitors. A signed-in user's Messages accept only the panel's widget token from the page's current `identify` (never the reader cookie), and the panel drops it when the page signs someone else in or out. A signed-out visitor is asked for their email before their first message (so the team can follow up after they leave) and gets a visitor token (random, stored hashed, kept in the widget's storage for 30 days and dropped when the page signs someone in), which shows them their own conversations and nothing else. Their email is never verified and never linked to a user: the conversation is with that address, marked not verified, and replies they haven't seen go to it by email. When a project user has that address, the team sees them beside the conversation as "Maybe <name> (not signed in)", a hint to look at, never merged: nothing about that user is shown to the visitor, and their conversation stays apart from the user's. "Ask a person" from someone signed out starts such a conversation. An email is matched to the project's user with that address (verified portal account first, then the SSO email) only when it passed DMARC at the receiver; anything else stays an email-only person the team can see is unverified.
- **Receiving email: forwarding, then a signed POST.** Each project gets its own support address on a domain used only for support email (`SUPPORT_EMAIL_DOMAIN`; on tuti.so it's `tuti.email`, bought 2026-10-27, apart from `mail.tuti.so`, which sends Tuti's own email, so support mail and its reputation stay separate from Tuti's): `support@<slug>.tuti.email`, the project's own subdomain, like its portal at `<slug>.tuti.so` (not `<slug>.tuti.so` itself: portals reach the app through a Cloudflare Tunnel, whose CNAME can't share a name with an MX record). The mail subdomain is chosen from the slug when the project first gets one (with a number added if it's taken, `acme-2`), belongs to that project for good and is never given to another, even after the project is deleted; it doesn't follow later slug changes (the portal's slug can be reused as today, the mail subdomain can't), so mail to an address never reaches someone else. The address is both where the project's mail arrives and, until the team sends from its own domain, the From of its replies, so on any plan users can write to it directly. The team forwards its support address (support@acme.com) to it in its own mail provider; no DNS records on their domain. Setup shows the address, shows the confirmation email Gmail and others send to a new forwarding target (so its code or link can be used), and is verified once a test email arrives. The app receives mail only at `/api/inbound/email`: the raw message with the envelope recipient (forwarded mail often still says `To: support@acme.com`, and Bcc'd mail names nobody, so the project comes from the envelope, not the headers) and the receiver's SPF, DKIM and DMARC results, all signed together with `INBOUND_SECRET` (HMAC with a timestamp, 5 minutes' tolerance), so it needs no mail provider's code. What delivers it is the server's choice: on tuti.so, SES receiving (one wildcard MX, `*.tuti.email`, and one receipt rule for all its subdomains; Cloudflare Email Routing can't, with its catch-all only on a zone's apex and 30 domains a zone): SES stores the message in S3 and a small Lambda (kept in the repo, about 30 lines) posts it; self-hosted, a small SMTP receiver in the worker (`smtp-server`, already in the testkit) behind an MX record, or any mail server piping into it. Parsed with `mailparser` (already in the testkit).
- **Sending: Amazon SES over SMTP (decided 2026-10-27), the project's support address or the team's domain, as Featurebase does.** Replies go through the server's SMTP, with Reply-To the conversation's address (the project's address with `+<token>`), so replies come back even when a mail client drops the threading headers. From is one support address per project, with the replying teammate's name: "Jane at Acme <support@acme.com>" (what Help Scout, Front and Featurebase do; a teammate's own address would send the user's replies to that person's mailbox instead of the inbox). Until the team sets its domain up, From is the project's support address with that name ("Jane at Acme <support@acme.tuti.email>"); `tuti.email` is verified in SES once (DKIM, `bounce.tuti.email` for bounces, DMARC quarantine; set up 2026-10-27), which covers every project's subdomain, so a project needs no DNS records of its own (tested 2026-10-27: `support@acme.tuti.email` sends, with the configuration set too; item 7 checks it through a project's tenant over SMTP, and if SES refuses an inherited address there, Tuti adds each project's subdomain as its own identity instead). tuti.so sends all its email through SES (its SMTP interface, so `sendEmail` and Nodemailer stay; moving from today's provider is the SMTP settings), because SES can verify each team's domain by API and keep each project's sending apart. Sending as support@acme.com: the team enters the address, Tuti adds the domain to SES (`@aws-sdk/client-sesv2`, with the `SES_*` settings below) and shows the 3 DKIM CNAMEs SES gives, and "Check" asks SES whether they're verified (the domain is the project's alone: one already verified for another project is refused, since SES keeps one identity per domain). Each project is an SES tenant ("Standard" reputation policy, so SES pauses only the project whose mail draws bounces or complaints; its own suppression list, so an address that complained about one project isn't suppressed for another), and Tuti associates the support domain's identity, the configuration set and, once verified, the team's own domain with the project's tenant before its first message (SES refuses a message naming a tenant that a resource it uses isn't associated with) and every message from it names its tenant (`X-SES-TENANT`, and the configuration set that reports events). Bounces, complaints and deliveries come back from SES through SNS to `/api/email/events` (its signature checked, and only from `SES_EVENTS_TOPIC_ARN`: a valid signature only proves SNS sent it, and anyone can point their own topic at the endpoint; the subscription is confirmed only for that topic) and mark the message, found by the SES message id the SMTP reply gave when it was sent. SNS may repeat or reorder events, so each is kept once (by SNS's message id) and a message's state only moves forward (sent → delivered → bounced or complained): a late delivery never hides a bounce. A complaint also stops replies to that address by email for the project (shown on the conversation; the widget still works); SES's suppression list keeps Tuti from mailing a bounced address again. A server without SES (`SES_REGION` unset) sends replies from the project's support address through whatever SMTP it has (the operator sets that domain up with their provider), and "send from your own domain" isn't offered. On tuti.so (a server selling plans), projects email their users from the start (decided 2026-10-28: approving each new project by hand made trying Tuti slow), and their email is watched instead: each email is tagged with its project, SES's events count what each project sent, bounced for good and drew complaints per day, a project sends up to 200 emails a day in its first week, and one whose bounces (over 1.5% once it has sent 100) or complaints (3 above 0.03%, or 5) over two weeks pass 30% of SES's review levels is paused until the operator resumes it (`APP_PORTAL_OWNER` gets the link, the team an email saying why); self-hosted, none of it.
- **Threading,** in this order: the reply token in the address it was sent to, then `In-Reply-To` and `References` against the `Message-ID`s of messages Tuti sent (as delivered: SES replaces the `Message-ID` with its own, so the one its SMTP reply gives is stored; it contains a random UUID); else a new conversation. `Message-ID`s of received mail never join anything: the sender chooses them and every recipient of that mail has a copy, so they're kept only to show the thread. Either match joins a conversation only when the sender is its user or an address already in it (the To or Cc of one of its messages), and the mail passed DMARC (which proves the domain, not the mailbox: the random token or Tuti's `Message-ID`, sent only to that mailbox, is what stands for it, so a colleague at the same domain needs both the address and the secret. The secret is a bearer credential, as in every helpdesk's reply address: whoever the user forwards a reply to can write into the conversation as them, and a mail provider letting its users send as each other's addresses is outside what Tuti can check. Tests cover a same-domain sender with another's address and no secret (a new conversation), with the secret (joins, as designed), and with the user's address and a `Message-ID` copied from the user's own received mail but no secret (a new conversation)); anyone else starts a new conversation, so knowing a `Message-ID` or a forwarded reply address never lets someone write into another person's conversation. Nothing guessable (a `#12` in the subject) ever matches. Someone in Cc who replies is shown as such and doesn't change who the conversation is with.
- **Noise and loops.** Ignored, with the reason kept: `Auto-Submitted` other than `no`, `Precedence: bulk/junk/list/auto_reply`, out-of-office headers, mail from the project's own addresses or a no-reply one, and our own `X-Tuti-Loop` header. Bounces mark the message they're about as bounced (from SES's events; on a server without SES, a delivery report that reaches the inbound address). A new conversation from mail that failed DMARC is marked spam (shown under Spam, nothing notified). Every email Tuti sends on its own carries `Auto-Submitted: auto-generated`.
- **Reaching the user.** Every message from the team that the user hasn't seen a minute after it was sent is emailed to them, the unseen ones together in one email. A cron job every minute does it (claiming each message before sending, so two runs send once; a claim not marked sent within 10 minutes, a run that died, is taken again, so a message may rarely go twice but is never lost), so there's no new kind of delayed job. Reading a received email is a job per `inbound_email` that is safe to run again: the message keeps the row's id (unique), and adding it, the row's new status and the notifications to send are one transaction, so two runs at once (with or without a `Message-ID`) add and notify once. Seen means shown in the open widget, so someone chatting gets no email, and someone who started by email gets every reply a minute later.
- **Live: Server-Sent Events + Postgres `LISTEN/NOTIFY`.** A change commits with a `NOTIFY` (in the same transaction, so it's sent only once committed) naming the project, the conversation and its user, never content; each web instance keeps one `LISTEN` connection and passes each one on only to the streams allowed to see it (the project's team, and the widget of that conversation's user), so nobody learns of others' conversations; a stream ends when its session or widget token does, when the widget signs someone else in or out, and when a team member is removed; a client that hears of a change fetches it through the usual actions, so access is checked in one place. The app's inbox listens with its session cookie; the widget reads its stream with `fetch` and its widget token in a header (no token in a URL). A client fetches the current state each time its stream opens or reopens (`NOTIFY` only reaches those already listening, so a change made meanwhile would otherwise be missed). A comment every 25 seconds keeps proxies (Coolify's Traefik, Cloudflare's 100-second limit) from closing it, and a lost stream reconnects; where a stream can't stay open, the clients poll every 10 seconds. Next.js route handlers can stream, so no custom server or WebSockets. A user is online while their widget stream is open or for 2 minutes after their last request (`lastSeenAt`, written at most once a minute).
- **AI follows the existing rules.** A new AI feature, `support` (`AI_MODEL_SUPPORT`, metered and charged in credits): the escalation's summary becomes a note on the new conversation; a suggested reply from the docs (the same gate as AI answers decides whether the docs can answer; the model writes only then; the team edits and sends it); a summary of a long conversation on request. Nothing is sent to a user without a team member, until a later opt-in AI first response.
- **Notifications.** By email to the team: a new conversation goes to its assignee, or to every team member who has "Email me new conversations" on (on by default; a setting in the inbox); a user's reply goes to the assignee, or, when the conversation has none, to the same team members. A count of open conversations in the sidebar and in the tab's title, kept live by the stream.
- **API, MCP and webhooks.** Operations as everywhere: `conversations.list` (status, assignee, channel, user), `conversations.get` (with its messages), `conversations.create` (for a user, by your app's id or an email, like `author` today), `conversations.reply` (as the team, or as the user with `author`), `conversations.update` (status, assignee, spam), `conversations.note`, `support.get` / `support.update` / `support.verify` (settings). Access: conversations for the whole team, settings for owners and admins; each goes into the operations and authorization matrices. Webhooks `conversation.created` and `conversation.message_created` (from the user only, so a team's own replies don't echo back to it).
- **Server settings (self-hosted too).** All optional; each one turns on a part, and without them the inbox still works in the widget and the app. Added to `apps/web/.env.example` and `docs/support-email.md`:

## Redesign: what people use most, first (asked 2026-10-30)

A review of every screen (the team's app, Customize and Settings, the portal, the widget, at phone width too, and the marketing site) found the same few problems everywhere:

- **Lists are forms.** Feedback's rows carry two dropdowns each (board and status), Team's rows a role dropdown, the changelog editor a checkbox for every post. Nothing in them can be scanned.
- **The busiest pages are the narrowest.** List-and-detail pages (Feedback, Inbox, Users, a post) sit in max-w-4xl and leave much of a laptop's screen empty while they scroll.
- **Settings are in four places.** Settings' eight tabs, Customize (AI answers, Address), page headers (the changelog's Writing style, Boards' form) and Team at the top level. Support's settings alone are in three.
- **Who is asking isn't shown where the team decides.** Users' plan, company and MRR are synced, but Feedback, a post and the roadmap only count votes.
- **Nothing can be found by name.** No search on Feedback (the team's or the portal's), no ⌘K.
- **The order isn't by use.** Home only lists code changes (empty until GitHub is connected); Feedback opens on every status by votes, shipped and closed posts among open ones; the portal's boards mix shipped ideas in and don't show a signed-out visitor how to post; the widget's Feedback tab can't browse or vote; the sidebar is twelve items in one list.

Decided (2026-10-30), and written into design.md by the PR that first follows each:
- A list is read first: a row shows values, changed on click, in a preview pane or in bulk; no form controls in rows.
- List-and-detail pages (Feedback, Inbox, Users, a post) take the whole width, with a preview pane or a properties sidebar; forms and writing keep the narrow column.
- Customize is how the portal and the widget look, beside the preview; everything else is in Settings, in one grouped menu. No page keeps settings of its own in its header.
- No sentence under a page's title: what a page is for goes in its empty state, or a tooltip.
- A status has a colour dot beside its badge (Open grey, Under review amber, Planned dark green, In progress orange, Completed green, Closed light grey), so a list of mixed statuses can be scanned.
- One primary button per screen (already the rule; Code changes, the changelog editor and Billing break it today).

Order: the bugs and quick wins, then Autopilot (the next section), then the app's structure, the team's daily pages, the portal, the widget and the first run. Each item is a PR of its own (bigger ones split), with its journey updated and a screenshot of the changed screen.

## Autopilot (asked 2026-10-30)

Code changes is Tuti's strongest feature, and its name says the least about it. It becomes **Autopilot**: when a pull request merges, Autopilot finds the feedback, docs and changelog it changes. What it's sure of goes out by itself after a hold; the rest waits for the team, who are emailed and approve from the email in one click.

This changes the shipped loop's rule (Code changes: "nothing customer-facing changes until someone applies it"; "Applying by itself": completing a post, a team comment and publishing an article "always wait for someone"). Article edits and moving posts to In progress (with the team's comment) may now go out by themselves, after a hold, when Autopilot is sure and the post or article doesn't reach many people; owners can turn either off. Completing a post, which emails its people, still waits for someone unless an owner turns it on.

Decided (2026-10-30):
- **Words.** "Autopilot" wherever people read it: the sidebar, its pages, Home, Settings, emails, the docs and the landing page. API, MCP and webhook names stay (`codeChanges.*`, `codeChangeActions.*`, `code_change.ready`), so integrations keep working. Inside it: a shipped change (a merged pull request) and its updates; Closes the request (resolves), Progress update (moves forward), Link, Out of date and Missing info (an article now wrong, or missing something), New article, Changelog line; Approve (apply); Likely and Not sure (likely, maybe).
- **What it does by itself**, by default: links posts, writes the changelog line into the running draft and drafts new articles at once (only the team sees them); publishes article edits and moves posts to In progress with the progress update after the hold. Completing posts: "Ask me" by default, and owners may turn it on. Only owners change these.
- **Always waits for someone**, whatever the switches: an update below 95% sure; a post whose voters, commenters and author are 25 or more; an article with 500 or more views in the last 30 days. Owners change the three numbers.
- **The hold.** 24 hours by default; owners change it. Nothing customers see happens before it ends. At its end each update is checked again (still sure, its post or article unchanged since, its reach under the limits) and goes out, or waits for someone if it no longer qualifies.
- **Email buttons act in one click, for the person they were sent to, signed in.** Approve, Publish now and Stop do what they say when that person is signed in, then show what was done, with Undo. Signed out, they sign in first and it's done after. Each link carries a signed token for its recipient, its change and its button (7 days), so a link opened by anyone else (a forwarded email, another team member) only opens the review page with those updates ticked, to confirm there. Mail scanners open every link in an email but have no session, so they only reach the sign-in page. Review always opens the page.
- **Who's told.** Owners by default; a project setting adds admins or chosen team members. Each person picks: as they happen (merges minutes apart in one email), a daily digest, or off. Updates that will go out by themselves are always emailed to the owners as they happen, whatever they picked, so the hold never passes unseen; the digest gathers what waits for approval.
