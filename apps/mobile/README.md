# Tuti for iOS and Android

The Inbox on a phone (`docs/plan.md`, "Mobile app"). React Native with Expo; routes live in `src/app`.

```sh
pnpm --filter @tuti/mobile start    # the dev server (Metro), for a development build
pnpm --filter @tuti/mobile build    # bundle for both platforms, as a store build would (part of `pnpm build`)
```

The app runs as a development build, not in Expo Go: Google's and GitHub's sign-in come back to the app through its
own `tuti://` scheme, which Expo Go doesn't have. Build one on Expo's servers, from `apps/mobile` (where `eas.json` is), with
`npx eas-cli build --profile development --platform ios` (a simulator build) or `--platform android` (an APK),
install it, start Metro, and open the app. Point "Self-hosted server" at a local server (`http://localhost:3100`;
on an Android emulator, forward the port with `adb reverse tcp:3100 tcp:3100`).

Where things are: routes in `src/app` (signed out: `sign-in`; signed in: everything else, guarded in `_layout.tsx`),
the API client in `src/lib/api.ts`, the session in `src/lib/session.tsx` (`useSession()`, and `useApi()` for a
signed-in screen: `await api<{ conversations: … }>("/conversations?view=mine")` calls the operation as the teammate,
in their chosen project), signing in in `src/lib/sign-in.ts`, the colours in `src/lib/theme.ts` (`useColors()`), the Inbox's
list in `src/lib/inbox.ts` (`src/app/index.tsx` is the Inbox, `src/app/inbox/projects.tsx` its project sheet on Android,
`src/app/inbox/snooze.tsx` a swiped row's snooze choices: iOS's action sheet, Android's bottom sheet),
a conversation in `src/app/conversation/[number].tsx` (the Inbox opens it; `tuti://conversation/12` too; in a window 600 points or more both ways, `src/lib/layout.ts`, it's shown beside the Inbox's list instead, as the Inbox route's `?c=`) with its calls,
drafts and live updates in `src/lib/conversation.ts`, its details sheet (who it's with, assign, snooze, close, spam) in `src/app/conversation/[number]/details.tsx` with its calls in `src/lib/details.ts`, the Inbox's live stream in `src/lib/live.ts`, what's kept to read offline in `src/lib/offline.ts` (forgotten with the session), and notifications (permission, the device's registration, a tap's
conversation) in `src/lib/notifications.ts`, with their settings in `src/app/notifications.tsx`. Components that
aren't routes go in `src/components`.

Tests: `src/lib` with Vitest (`*.test.ts`, the repository's `pnpm test`); screens with React Native Testing Library
under Jest and `jest-expo` (`__tests__/*-test.tsx`, `pnpm --filter @tuti/mobile test`, which `pnpm test` also runs). A
screen test mocks the native header (`expo-router`'s `Stack`) and the session as `__tests__/inbox-test.tsx` does;
`jest.setup.js` draws a swipeable row with its actions showing (Reanimated, which moves it, doesn't run under Jest).

React, React Native and the Expo packages stay on the versions the app's Expo release supports: `pnpm lint` fails
when one drifts, and `pnpm --filter @tuti/mobile exec expo install --fix` puts them back.

`ios/` and `android/` are generated by Expo and never committed: native settings go in `app.config.ts`.
A build belongs to the Expo account and project in `EXPO_OWNER` and `EAS_PROJECT_ID`, and uses the app id
in `APP_ID`, so a fork builds its own app without changing this directory. Expo's builders read `app.config.ts` again
with only the EAS environment's variables, so `EAS_PROJECT_ID` and `EXPO_OWNER` are set there too, in each
environment (development, preview, production): a build without the project would get no push token, and is refused. Android's push tokens need the app's
Firebase config: `GOOGLE_SERVICES_JSON` is its path, an EAS file variable on Expo's builders.

## Builds and updates

Three build profiles in `eas.json`, each on its own update channel. Run them from `apps/mobile`, with `EXPO_OWNER` and
`EAS_PROJECT_ID` set as for any build:

```sh
npx eas-cli build --profile development --platform ios       # a simulator build that loads its JavaScript from Metro
npx eas-cli build --profile development --platform android   # the same, an APK
npx eas-cli build --profile preview --platform all           # installable builds for testing: an APK, and an iPhone build for registered devices
npx eas-cli build --profile production --platform all        # store builds (submitted by hand, not from here)
```

Fixes to the app's own code (JavaScript, images) go out without a store review as an over-the-air update, to the
builds on one channel, with that channel's EAS environment (`--environment` loads the same variables and files the
build had):

```sh
npx eas-cli update --channel preview --environment preview --message "What changed"
npx eas-cli update --channel production --environment production --message "What changed"
```

An update reaches only builds with the same native code: the runtime version is the fingerprint of everything native
(the native modules, their patches in `patches/`, and `app.config.ts`). A change to any of those needs a new build, and
updates published after it go to the new builds only.
